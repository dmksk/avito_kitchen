# Авито.Кухня

MVP backend-сервиса доставки еды, разработанный в рамках тестового задания
для стажёра Backend.

Система позволяет клиенту просматривать заведения и товары, оформлять заказы,
а заведению — проверять товары и управлять состоянием заказа.

## Основные возможности

- создание и получение заведений;
- создание и получение товаров заведения;
- фильтрация недоступных товаров;
- создание заказа;
- сохранение цены и названия товара на момент заказа;
- проверка актуальной цены и остатка через отдельный сервис заведения;
- получение списка заказов;
- получение отдельного заказа;
- изменение статуса заказа;
- обработка отсутствующих товаров, изменения цены и недостаточного остатка;
- автоматическая OpenAPI-документация;
- миграции базы данных;
- запуск всей системы через Docker Compose.

## Архитектура

Проект состоит из трёх контейнеров:

- `main-service` — основной FastAPI-сервис;
- `establishment-service` — демонстрационный сервис ресторана Pizza House;
- `postgres` — PostgreSQL 17.

Основной сервис является источником истины для заказов. Перед сохранением
заказа он обращается к Pizza House и проверяет актуальные цены и остатки.

## Запуск

Требуется установленный Docker Desktop.

```bash
docker compose up -d --build
```

При запуске основной сервис автоматически применяет все миграции Alembic.

Проверить состояние контейнеров:

```bash
docker compose ps
```

Все контейнеры должны иметь состояние `healthy`.

Остановить проект:

```bash
docker compose down
```

Удалить контейнеры вместе с локальными данными PostgreSQL:

```bash
docker compose down -v
```

Последняя команда удаляет локальную базу данных и предназначена только для
сброса тестового окружения.

## Подготовка демонстрационных данных

После первого запуска создайте заведение через:

```text
POST /establishments
```

```json
{
  "external_id": "restaurant-001",
  "name": "Pizza House",
  "establishment_type": "restaurant",
  "address": "Moscow, Lenina 10"
}
```

Затем создайте товар для полученного `establishment_id`:

```text
POST /establishments/1/products
```

```json
{
  "external_id": "pizza-margherita",
  "name": "Маргарита",
  "description": "Томатный соус, моцарелла и базилик",
  "category": "pizza",
  "price": 599.00,
  "is_available": true
}
```

`external_id` и цена должны совпадать с данными демонстрационного сервиса
Pizza House.

## Пример создания заказа

```text
POST /establishments/1/orders
```

```json
{
  "customer_name": "Анна",
  "customer_phone": "+79990001122",
  "delivery_address": "Москва, Тверская, дом 5",
  "items": [
    {
      "product_id": 1,
      "quantity": 1,
      "expected_price": 599.00
    }
  ]
}
```

Перед сохранением заказа основной сервис:

1. проверяет существование заведения;
2. проверяет товар в своей базе;
3. сравнивает цену, которую видел клиент;
4. обращается к Pizza House;
5. проверяет актуальную цену и остаток;
6. сохраняет заказ и снимок товара.

## Конфликты при оформлении

Если товар закончился, его цена изменилась либо он отсутствует, API отвечает
кодом `409 Conflict`.

Пример:

```json
{
  "detail": {
    "message": "Order cannot be created",
    "conflicts": [
      {
        "type": "price_changed",
        "external_id": "pizza-margherita",
        "old_price": "599.00",
        "new_price": "649.00"
      }
    ]
  }
}
```

Если сервис заведения недоступен, возвращается `503 Service Unavailable`.

## Статусы заказа

Допустимый жизненный цикл:

```text
pending
  ├── accepted → preparing → ready → in_delivery → delivered
  ├── rejected
  └── cancelled
```

- `rejected` устанавливается заведением;
- `cancelled` устанавливается пользователем;
- для отклонения заказа требуется причина;
- недопустимый переход возвращает `409 Conflict`.

## Основные маршруты

### Main Service

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/health` | Проверка состояния |
| GET | `/establishments` | Список заведений |
| POST | `/establishments` | Создание заведения |
| GET | `/establishments/{id}/products` | Меню заведения |
| POST | `/establishments/{id}/products` | Создание товара |
| POST | `/establishments/{id}/orders` | Создание заказа |
| GET | `/orders` | Список заказов |
| GET | `/orders/{id}` | Получение заказа |
| PATCH | `/orders/{id}/status` | Изменение статуса |

### Pizza House

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/health` | Проверка состояния |
| GET | `/menu` | Актуальное меню |
| POST | `/integration/orders/validate` | Проверка заказа |
| PATCH | `/menu/{external_id}/stock` | Изменение остатка |
| PATCH | `/orders/{id}/status` | Передача статуса в Main Service |

## База данных

Используются таблицы:

- `establishments`;
- `products`;
- `orders`;
- `order_items`.

Денежные значения хранятся как `NUMERIC(12, 2)`. В `order_items`
сохраняются название и цена на момент заказа, поэтому исторические данные
не зависят от последующих изменений меню.

Схема управляется миграциями Alembic. Создание схемы через
`Base.metadata.create_all()` не используется.

## Ограничения MVP

- авторизация отсутствует согласно условию задания;
- клиентская часть не реализована;
- меню демонстрационного заведения хранится в памяти;
- нет платёжной интеграции;
- нет службы курьеров;
- нет распределённой транзакции между сервисами;
- нет резервирования остатка товара;
- адрес доставки хранится текстом без геокодирования;
- секреты в Compose предназначены только для локальной демонстрации.

Для production-версии потребуются авторизация, Redis, брокер сообщений,
идемпотентность запросов, наблюдаемость, безопасное хранение секретов,
резервирование товаров и асинхронная обработка событий.

## Использование ИИ

ИИ использовался как помощник для:

- декомпозиции бизнес-сценариев;
- обсуждения архитектурных решений;
- подготовки отдельных фрагментов кода;
- поиска ошибок;
- формирования тестовых сценариев и документации.

Основной план работы:

```text
1. Определить CJM пользователя и заведения.
2. Спроектировать сущности и связи базы данных.
3. Реализовать Main Service слоями: API, schemas, services, models.
4. Добавить миграции Alembic.
5. Реализовать отдельный сервис заведения.
6. Добавить межсервисную проверку цены и остатка.
7. Настроить Docker Compose.
8. Добавить OpenAPI, тесты, линтер и документацию.
9. Проверить основные и ошибочные бизнес-сценарии.
```

Принятые архитектурные решения и сгенерированные участки были проверены
через Swagger, Docker healthcheck, Ruff и Pytest.
